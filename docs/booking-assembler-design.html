Trackplan — design notes

Trackplan places ordered booking legs onto a network of Stations (see BUILD_SPEC for StationType / Tasking). This HTML still uses older Class/Car/Yard labels in places — narrative only until a rename pass.

Why this doc

This captures interactive walkthroughs for Trackplan: vocabulary, the two-layer algorithm (Assembler + Coupler), performance, failure reporting, and how we stop the yard mesh from exploding.

Format: HTML for interactive diagrams and walkthroughs. Index: docs/README.md. Deep-link a scenario with ?scenario=simple|multiyard|loopback|prefilter|nosol|sticky.

Terminology (rail model only)

Use these words in product, code, and docs. Avoid domain synonyms unless bridging to an older system.

TermMeaning
Class A catalog role or car-kind you can request (e.g. Refrigerated, Normal, Docking). Many Cars implement one Class.
Car One concrete unit of a Class (identity you can claim).
Setup Costly mode on a Car or Yard. Changing setup takes time and may drop live traffic. Prefer reuse / piggyback. Each Class has its own allowed Setups.
Inspector Per-Class rules (unique implementation) that answer: “Does this Car — with its live config/Setup — satisfy leg request X (and Context)?” Catalog Setup names the mode; the Inspector proves fitness of a concrete Car for that request. Also called a clearance check in ops prose.
Booking One end-to-end reservation: ordered legs, bound Cars, route hops, context, sticky snapshot.
Leg One line on a Booking: required (Class, Setup) plus any Class-specific request fields the Inspector understands. Fulfilling a leg usually adds one Car to the consist.
Consist The train so far — ordered Cars already claimed for this Booking. Length grows: 1 → 2 → 3 …
Context Accumulated facts that later Inspectors (and path rules) consume. Sources are not only bound Class Cars — Yards (and other path devices) can publish facts when visited (e.g. a clearance stamp from Yard 2). Missing path-context can force detours/loopbacks even when a shorter cable to the next Car exists.
Yard Junction with numbered in / out tracks and a legal in→out map (not always full N×M).
Track / port Attachment point: (device, in|out, track_id).
Hop One visit: in:device:out (enter on track in, leave on track out).
Route Ordered hop list realizing couplings for the Booking.
Cable External edge from one device’s out track to another’s in track.
Checkpoint Class policy: once a Car of that Class is claimed, other Cars of that Class are not tried (class-once).
Assembler Outer engine: walks legs, picks Cars, holds context, calls Coupler, checkpoints, sticky, failures.
Coupler Inner engine: bounded multi-sink BFS/A* on the port graph through Yards for one coupling segment.
Oracle Precomputed reachability / distances on ports for fail-fast and A* heuristics.
Fingerprint / hopeful token Version of world inputs so we can reuse SAT/UNSAT without re-search when nothing relevant changed.

Yard type sketches

Direct

in k → out k only. No re-addressing inside the box.

Aggregator

Many ins → one Ag out (1→Ag, 2→Ag, …).

Expander

One Ag in → many outs (Ag→1, Ag→2, …).

Restricted / full matrix

Sparse or dense legal crosspoints; full N×M is the extreme.

Big picture

A Booking is not “visit places on a map.” It is assembling a longer train: each leg claims a Car of the required Class/Setup, optionally through Yards, and publishes facts that constrain the next leg.

Outer vs inner

Outer Assembler

Walk legs in order. For each Class, run that Class’s cheap prefilter (mini-inspector) to build Coupler goals. Rank, call Coupler; full accept() runs at goal arrival. Bind Car, merge facts, checkpoint, sticky/fail.

Inner Coupler

One segment: start = consist tail port, goals = candidate head ports. Bounded multi-sink BFS/A* on the port graph (cables + legal Yard in→out).

Contract: Assembler runs Class legs and Booking state. Coupler finds one successful path between two Classes (any number of Yards in the middle) — early return on success, or fail when search is exhausted. Assembler does not get a callback after every failed path try.
AssemblerCoupler (A*/BFS)
Main use Class leg order, candidate Cars, Context, checkpoints, sticky, whole-Booking fail Fabric path from tail Car to some next-Class Car
How often they talk Once per Class→Class segment (after first Car) Many expansions inside one call; one return to Assembler
Success Bind car, append full hop list from Coupler Early return: path + car when goal port + Inspector OK
Failure Booking UNSAT at this leg Open set empty / budget — no acceptable path
Yards Never steps Yards as legs 0..many Yard hops between the two Classes (any types)
Wrong A* returns R→Y1→N4 → Assembler Inspector-fails → Assembler starts a new A* for R→Y2→N4
Right Short-path fail, other N tries, Y2 discovery all happen inside one couple(); Assembler only sees final success or total fail 
// Assembler control flow
for each Class leg:
  candidates = Inspector-filter + rank
  if first leg:
    bind Car only (no Coupler)
  else:
    result = Coupler.couple(tail → candidates, context)  // BLOCKED until done
    // inside Coupler: try short paths, fail Inspector, expand Y2, …
    if fail: Booking UNSAT
    bind result.car; route += result.hops; context = result.context


// Coupler — one segment only
couple(start_ports, goal_cars, context):
  multi-sink A*/BFS on port graph
  on reach goal Car:
    if Inspector.accept(..., path_context): return success  // early
    else: discard, continue
  if exhausted/budget: return failure
A → Z with only Yards between? Still one Coupler call. Path may be A-car → Y₁ → … → Y₁₂ → Z-car. Twelve yard types = edge rules on the fabric, not twelve Assembler steps. Full picture + open questions: docs/SPEC.md. Implementer contracts: docs/BUILD_SPEC.md §8.0.

Assembler (deep dive)

The Assembler’s main use is to turn a multi-Class Booking into a sequence of “pick next Car + connect from previous,” using Coupler as the fabric engine for each segment. It does not expand every Yard track. It holds consist, Context, checkpoints, and sticky/fail.

What it stores between legs

MemoryFeeds into
Consist (Cars bound)Answer + sticky replay
Context factsFilter next candidates before A*
Tail port of last CarStart of next Coupler run
Route hops so farFull Booking route
Checkpoints (closed Classes)Cull other Cars of that Class

Why outer is serial

Later eligibility depends on earlier binds (context). You cannot freely assign all Classes in parallel and join paths afterward. Parallelism is fine inside a leg (filter/rank) or inside Coupler precompute — not across legs as independent solves.

Checkpointed Classes

When a Class is checkpointed (class-once), claiming a Car freezes that Class for the Booking. Failures after that leg are reported as conditional on the lock:

“Failed at Docking under checkpoint Refrigerated = R-17. Other Refrigerated Cars were not considered.”

Coupler — multi-sink bounded A* / BFS

Each coupling segment is a normal shortest-path problem on ports, not on Class labels. 

// One leg's fabric search
starts = tail ports of consist (e.g. last Car's outs)
goals  = head ports of ranked candidate Cars for this Class

search = BFS if unit hop cost
       = A*  if weighted cost + heuristic from Oracle

until hit any goal OR budget exhausted:
  expand via cables and legal Yard (in→out) pairs
  prune: repeat hop_key, hop budget H, visits/yard V, max expansions

Why multi-sink (not one A* per Car)

One search from the tail toward all candidate ports explores the Yard fabric once. Prefer that over N independent A* runs that re-walk the same corridors.

Two reasons for multi-Yard loopbacks

CauseWhat forces the detourExample
Track / map Legal in→out pairs (or cables) do not allow the short hop Yard1 forbids 1→6; only 5→6 reaches the cable to the next Car
Context / Inspector Short cable exists, but next Class Inspector fails without facts gained only by visiting another Yard (or device) first Yard1→Kind D is wired, but DockingInspector needs a stamp from Yard2 → path must hit Y2, loop back, then Kind D

Both can combine on one Booking. Coupler state may need more than ports: port + partial Context acquired along the path (or mandatory waypoints derived from “what facts does this leg still need?”).

Useful re-entry vs infinite loopback

Walkthrough 3 · Loopback shows a good re-entry: 1:Y1:2 then later 5:Y1:6 (different hop_key) after Y2→N-04 is closed. The same fabric can thrash forever if Coupler keeps expanding Y1↔Y2 on already used ports with no new facts.

Rule of thumb: re-visit a Yard only when the hop_key = (device, in, out) is new or path Context improved. Same hop_key again = spin → prune. Still over-visit? Hard caps → BUDGET.
Guard (DEFAULT v1)Allows useful re-entry?Stops infinite loopback?
No repeat hop_key on path Yes — 1:Y1:2 then 5:Y1:6 OK Yes — cannot expand the same in→out again
max_visits_per_yard V (default 3) Yes if within V Yes — even with many distinct hop_keys
max_hops H (default 16) Short detours OK Yes — path length wall
max_expansions + max_wall_ms — Yes — mesh thrash → finite BUDGET, never hang
Optional no immediate cable backtrack Usually Culls trivial A→B→A edges
Closed set (port, context_fp) Yes — stamp later can reopen goal logic Avoids re-expanding same state

Golden G1 = restricted re-entry succeeds (two Y1 hop_keys). Golden G2 = caps prevent infinite y1↔y2 (finite UNSAT / BUDGET). Spec: BUILD_SPEC policy + Coupler prune; SPEC hop_key anti-loop.

Restricted Yard forces detour (example)

Yards, tracks, hop syntax

Graph nodes for Coupler are ports, not whole devices. Edges are (1) cables out→in and (2) legal internal pairs inside a Yard. 

hop syntax:  in : device : out
example:     5 : yard1 : 6     // enter yard1 on 5, leave on 6

Direct Yards only allow matching numbers. Aggregators / expanders introduce shared Ag ports with their own capacity rules (mutex vs combine — product policy).

Heuristics we rely on

HeuristicLayerEffect
Checkpoint / class-once Assembler After claim, drop other Cars of that Class. Sub-optimal by design; huge cull.
First-fit on stable order Assembler Deterministic; sticky id first; no full optimality.
Piggyback Setup Assembler rank Prefer Cars already in required Setup (reconfig is expensive).
Sticky snapshot Resolve entry Same Booking + valid world → same Cars/route; skip search.
Context filters Assembler Facts from earlier Cars shrink next candidate sets before A*.
Multi-sink couple Coupler One fabric search per leg toward all candidates.
Oracle reachability Before Coupler Drop geometrically impossible goals within H (optimistic vs capacity).
Hop / visit / expansion budgets Coupler Hard cap mesh thrash; may yield BUDGET failures.
No repeat hop_key Coupler Kill y1↔y2 livelock; keep legal re-entry on new tracks.

Performance

Dominant cost is almost always: 

time ≈ Σ_legs ( candidates_tried × cost(couple_search) )

Drive both factors down.

Hot path

  1. Sticky hit → return snapshot (fastest).
  2. Per leg: index by Class/Setup → context filter → rank → oracle prune.
  3. One multi-sink bounded A*/BFS (not one search per Car).
  4. Hard caps: H, V, max_expansions, wall clock.

Data structures (Coupler hot loop)

  • Integer port ids; CSR adjacency for cables + Yard maps.
  • Sparse internal maps (only legal pairs).
  • Visited on port (and visit count if V>1).
  • No string labels inside expand.

Complexity intent

ModeCouple searchesQuality
Sticky hit0Previous
First-fit multi-sink / leg~1Sub-optimal OK
Beam / backtrack reopen checkpointmultipliesHigher success
Performance is an SLA + caps contract, not “run until optimal.” Measure sticky hit rate, candidates entering Coupler, expansions/leg, oracle reject rate.

Graph explosion — more levers

Yards are N:M and Yard–Yard meshes can explode. Beyond the heuristics above:

Discussed

  • Port-level state + hop_key anti-loop
  • H / V / max expansions
  • Oracle + A* heuristic distances
  • Multi-sink; checkpoint; context prune
  • Negative cache so failed Bookings do not rescan when nothing hopeful changed

Additional ideas (not fully designed yet)

TechniqueIdeaTradeoff
Yard clustering / contraction Collapse dense Yard regions to boundary ports; precompute boundary→boundary costs; expand interior only when entered. Build complexity; rebuild on topology change.
Landmark / ALT heuristics Stronger A* h than plain BFS layers; fewer expansions. Precompute memory.
Bidirectional multi-sink Forward from tail + multi-source backward from goals; meet in middle (fabric only). Implementation care; still one leg.
Corridor / template routes For common Class pairs, preferred Yard corridors; search deviation only on miss. Ops knowledge; maintenance.
Hierarchical planning Region-level path first, then port refine. Two-level correctness.
Incremental Oracle Update reachability only for affected components on topology edit. Engineering cost.
Capacity-aware landmarks Coarse “region full” flags to skip hopeless clusters. Can be wrong if too coarse; keep optimistic fail-open carefully.
Beam on partial consists Keep k partial trains instead of pure first-fit — better success without full meta-A*. k× work.
Lazy Coupler Only run A* for top-ranked candidates after oracle; or stop at first goal in preference order. Default we want.
Separate geometry vs occupancy Oracle ignores live claims (optimistic); Coupler applies occupancy — avoids constant oracle rebuild. Some false-positive couple attempts.

Failure reasons

Do not narrate the A* open set. Fail at the first pipeline stage that empties options, and attach a small report.

Pipeline (explain at first zero)

Catalog → Inspector(request, car, context) → Busy → Oracle geometry → Free path → Budget

Inspector subsumes “Setup + Class-specific rules + Context consumption.” Prefer one reject reason from the Inspector when possible (structured), not a silent empty list.

Stable reason codes

CodeWhenUser-facing gist
NO_CANDIDATESNo Car passes this Class’s Inspector for the request/contextNothing fits this leg given earlier locks
INSPECTOR_REJECTOptional detail: Inspector returned a typed reason on sampled Carse.g. “Car config incompatible with request X”
ALL_BUSYMatches exist, all claimedMatching Cars all in use
UNREACHABLEOracle: no geometry within HNo Yard path to any matching Car
CAPACITY_BLOCKEDGeometry ok; hops/ports busyPaths blocked by other Bookings
BUDGETHit expansion/hop limitsNo path within search limits
CONTEXT_DEAD_ENDCheckpoints make later legs impossibleEarlier Car choices leave no continuation
POLICYRule forbids combinationDisallowed by policy

Failure report shape

{
  status: "UNSAT",
  failed_leg: 3,
  code: "CAPACITY_BLOCKED",
  summary: "…",
  checkpoints: [
    { leg: 1, class: "Refrigerated", car: "R-17" },
    { leg: 2, class: "Normal", car: "N-04" }
  ],
  counts: {
    candidates_before_context: 40,
    after_context: 12,
    after_busy: 5,
    oracle_ok: 3
  },
  blockers: [ { booking: "B-88", hop: "5:yard1:6" } ],
  suggestions: [ "Release B-88", "Reopen checkpoint on Normal" ]
}

Checkpoints let you scope the failure: it failed under these locks. That is not a proof another Car would work until you reopen and succeed.

Sticky success & negative cache

SAT (sticky)

Persist consist + full hop list + setups. On resolve, if still valid → return without re-search. Avoids needless re-Setup.

UNSAT (negative cache)

Cache failure + reason under a token of hopeful world inputs. Do not thrash thousands of Cars when nothing that could open a solution changed.

EventRetry failed Booking?
Other Booking claims more capacityNo — world tighter
Release of claimsYes
Setup unlock / change that enablesYes
New cable / legal Yard pairYes
New Car onlineYes
Looser policy (higher H)Yes
This Booking’s legs editedYes

Yards are included: topology maps, Yard setups, and Yard occupancy all affect hopeful vs non-hopeful revisions.

Discussion map (how we “satisfy” each topic)

For each topic, you only need to confirm or override DEFAULTS — not redesign from zero:

  1. Data model — Confirm Port/Hop/Reservation shapes; any extra device kinds beyond Car/Yard?
  2. API — Library-only vs HTTP; auth out of scope?
  3. Policy numbers — Are H=16, V=3, max_expansions=50k, wall=500ms acceptable?
  4. Inspector — Real Class request schemas (beyond toy Refrigerated/Normal/Docking)?
  5. Yard capacity — Accept exclusive-only v1, or need combine/share day one?
  6. Facts — Production key names for stamps/cabinets; which Yards publish on hop?
  7. Claims — Hard reserve on SAT only (spec) vs hold during preview?
  8. Goldens — Extend G* with your real topology fixtures later.
  9. Stack — Language/DB choice (spec is language-agnostic).
