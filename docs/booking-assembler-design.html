Trackplan — design notes

Trackplan places ordered Booking legs onto a network of Stations (StationTypes) connected by Links on Tracks. Engines: Assembler (outer legs) + Coupler (inner path). User-visible plan path = Route. Canonical model: docs/BUILD_SPEC.md.

Why this doc

Interactive walkthroughs for Trackplan: Station vocabulary, Assembler + Coupler, Prefilter vs Inspector, performance, failure reporting, and how transparent path stations (e.g. switches) fill the fabric without becoming demand legs.

Format: HTML for interactive diagrams and walkthroughs. Index: docs/README.md. Deep-link a scenario with ?scenario=simple|multiyard|loopback|prefilter|nosol|sticky (scenario ids stable). Primary contracts: docs/BUILD_SPEC.md.
Walkthrough narrative: scenarios simplify full Task / time-slice / whole-booking commit mechanics from BUILD_SPEC. They teach Assembler vs Coupler and Prefilter vs Inspector.inspect, not every engine edge case.

Terminology (canonical Station model)

Use these words in product, code, and docs. Bridge from older names only when needed: Class/Car → StationType/Station · Yard → transparent StationType · Cable → Link · Port → Track · Consist (old project name) → Trackplan.

TermMeaning
StationType Catalog type: schemas, inspector, heuristics, transparent? (e.g. Refrigerated, Normal, Docking, Switch). Many Stations implement one StationType.
Station Instance of a StationType (id you bind): setup, tasking, liveData, tracks. Example ids: R-17, N-04, Y1 (Y1 = Switch Station).
transparent StationType omitted from Booking demand; Coupler path filler only (e.g. switch). Users do not author legs or requests for transparent types (v1).
Track Named IN or OUT endpoint on a StationType / Station. Ref: (stationId, in|out, trackId).
Link Physical topology edge: Station A OUT track → Station B IN track. Coupler may traverse only online Links.
Setup Semi-static station properties (schema on type, values on station). Not booking-driven; Assembler never mutates setup.
Task / Tasking Task = one use of a station (input, output, context, taskingConfiguration, bookingIds). Tasking = Task[] on a Station — live/planned-live source of truth.
Request User demand on a Booking leg (object shaped by StationType.requestSchema).
Prefilter Cheap screen before Coupler: canUse(setup, request, liveData) — no Task, no path context. Safe drops only (path could never fix).
Inspector Per-StationType: inspect(setup, tasking, request, liveData) → Task[] | Failure. Full assign when Coupler tries a candidate Task at a multi-sink goal or transparent hop (path context already seeded on the Task). Sole writer of Task.context.
Booking Demand legs + plan: bindings, route, failure, sticky. Commit is whole-Booking only.
Leg One demand line: non-transparent stationTypeId + request. Transparent types never appear as legs.
Route / Hop / Binding Route = full hop path after resolve (user-visible plan). Hop = in:station:out. Binding = this Booking uses this Station (leg or path).
Context Per-Task map of path/comms facts. Inspector only writes/extends keys (Coupler seeds the next candidate from the previous accepted Task.context). Transparent: inspect every visit (C2d) — e.g. Y2 Inspector may set clearance.y2_stamp for later legs.
Checkpoint StationType type-once: do not try other Stations of that type. DECIDED timing: only after the next non-transparent StationType has a successful working Task (or last leg SAT). Alts kept until then.
Assembler Outer engine: legs, Prefilter candidates, Oracle++ goals/alts, checkpoints, sticky, incremental re-resolve, whole-Booking commit. Serial per booking in a run (v1).
Coupler Inner engine: one multi-sink couple(tail, goals) per segment; ExpandKey frontier (not summed edgeCost / not f=g+h); transparent path fillers (inspect every hop).
Oracle++ Topology insight: reachability / terminal (and chain) filters for multi-sink goals; also feeds ExpandKey distToSegmentGoals / distToTerminal. Rebuild on topology change, not tasking. (Legacy “Oracle” = Oracle++.)
Agenda / goals Assembler-owned ExpandKey-sorted multi-sink targets (finishes of next type, Oracle++-filtered). One Coupler.couple(tail, goals); inspect fails stay inside the ExpandKey frontier. Unused goals = alts until the type is checkpointed.
Sticky (relevance-scoped) Cache SAT plan or UNSAT report under demand + relevant world epochs (BUILD_SPEC §3.10) — not a single global hopeful_rev as the validity contract.

Transparent path stations (legalPairs sketches)

No separate Yard entity. Switches and similar junctions are transparent StationTypes with IN/OUT tracks and legal in→out pairs. Coupler fills them between demand Stations.

Direct

in k → out k only. No re-addressing inside the box.

Aggregator

Many ins → one Ag out (1→Ag, 2→Ag, …).

Expander

One Ag in → many outs (Ag→1, Ag→2, …).

Restricted / full matrix

Sparse or dense legal crosspoints; full N×M is the extreme.

Big picture

A Booking is ordered demand legs (non-transparent StationTypes only). Assembler builds multi-sink goals and calls Coupler.couple(tail, goals) once per segment (first leg: virtual S0). Coupler fills transparent path stations (switches) and Links. After resolve the user may see a full Route: R-17 → Y1 → Y2 → N-04 → D-02. Task.context (Inspector-written) may require facts from earlier hops (e.g. Y2 stamp).

Outer vs inner

Outer Assembler

Walk demand legs in order (non-transparent StationTypes only). For each leg: Prefilter → Oracle++ filter/sort → multi-sink goals → one Coupler.couple(tail, goals) (first leg: virtual S0). Apply bind, tail = accepted Task.output out-track, checkpoint timing (C2c), sticky/fail. Whole-Booking commit. Serial one booking at a time in a run (v1).

Inner Coupler

One segment: start = tail out-track (accepted Task.output, e.g. R-17:out1) or virtual S0 for first type; goals = Oracle++-filtered finishes of next type. Bounded multi-sink search on Stations + Tracks + Links with ExpandKey frontier; transparent stations are path fillers — inspect every visit (C2d).

Contract (Option A — multi-sink): Assembler runs demand legs and Booking state. One couple(tail, goals) per segment finds a successful path to some goal (any number of transparent stations in the middle) — first-fit inspect OK, or fail when ExpandKey frontier / budget is exhausted. Path/inspect fails stay inside Coupler; Assembler does not peel targets or re-call per goal.

Assembler (deep dive)

The Assembler’s main use is to turn a multi-leg Booking into a sequence of “bind next demand Station + connect from previous,” using Coupler as the fabric engine for each segment. It does not expand every switch track. It holds bindings/route, Task context, agenda, checkpoints, and sticky/fail. Working tasking is path-local until whole-Booking SAT commits.

What it stores between legs

MemoryFeeds into
Bindings (Stations used)Plan + sticky replay
Latest accepted Task.context (copy)Seed next candidate Task; Inspector writes keys
Tail = accepted Task.output out-trackStart of next couple() (never Station alone)
Route hops so farFull Booking route (user-visible)
Checkpoints (closed StationTypes)Cull other Stations of that type; backtrack floor (C2b)
Agenda alts (unused multi-sink goals)Retained until type checkpointed; used if later leg fails and we backtrack to last Checkpoint

Why outer is serial

Later eligibility depends on earlier binds (context / tasking). You cannot freely assign all StationTypes in parallel and join paths afterward. Parallelism is fine inside a leg (Prefilter/rank) or inside Coupler precompute — not across legs as independent solves. v1: one booking at a time in a run; no force-kick of exclusive holds without a full re-plan pass.

Checkpointed StationTypes

When a StationType is checkpointed (type-once), its bound Station freezes for the Booking — other Stations of that type are never tried again on this resolve. DECIDED timing (C2c): checkpoint type T only after the next non-transparent leg has a successful working Task (or T is last leg and booking is SAT). Do not checkpoint Refrigerated until Normal has a working Task; do not checkpoint Normal until Docking OK (or SAT). Alts for T are kept until then. Failures after a lock are conditional:

“Failed at Docking under checkpoint Refrigerated = R-17. Other Refrigerated Stations were not considered.”

Coupler — multi-sink ExpandKey frontier

Each coupling segment is a path search on Stations + Tracks + Links, not on StationType labels alone. ExpandKey ranks legal neighbors (lexicographic); NeighborRank is component 4 (SmartNode). Oracle++ hop distances feed ExpandKey components distToSegmentGoals / distToTerminal (optimistic, ignore tasking) — not a competing classic A* f=g+h pop score. Goal set is built by Assembler via Oracle++ (reachability + terminal/chain) before the call. 

// One segment — Option A multi-sink (DECIDED)
starts = tail OUT track (accepted Task.output) | virtual S0 → first-type goals
goals  = sortByExpandKey(Oracle++ filter(Prefilter pool of next demand StationType))

search = frontier pop (g, ExpandKey…)   // ExpandKey-dominated; not f=g+h
// ExpandKey: preferInUse, preferNonTransparent, distToSegmentGoals, distToTerminal, neighborRank, names
// g = hop count only (hygiene); distToG lives inside ExpandKey

until first inspect-OK goal OR budget exhausted:
  expand via Links and legal in→out pairs on stations
  transparent hop: inspect every visit (may write Task.context)
  prune: repeat hop_key, hop budget H, visits/station V, max expansions
  at goal: inspect(setup, tasking+candidate, request, liveData); fail → continue frontier

Why multi-sink (not one search per Station)

One ExpandKey frontier from the tail toward all candidate stations explores the transparent fabric once. Prefer that over N independent single-sink runs that re-walk the same corridors (Option B peel — not v1).

Two reasons for multi-switch loopbacks

CauseWhat forces the detourExample
Track / legalPairs Legal in→out pairs (or Links) do not allow the short hop Y1 forbids 1→6; only 5→6 reaches the Link to the next Station
Context / inspect Short Link exists, but next-type inspect fails without facts gained only by visiting another transparent station first Y1→N is wired, but Normal inspect needs a stamp from Y2 → path must hit Y2, then N

Both can combine on one Booking. Coupler state includes more than tracks: hop path + Task.context flowing along the path (seeded into the next candidate; Inspector is the only writer of durable keys).

Useful re-entry vs infinite loopback

Walkthrough 3 · Loopback shows a good re-entry: 1:Y1:2 then later 5:Y1:6 (different hop_key) after Y2→N-04 is closed. The same fabric can thrash forever if Coupler keeps expanding Y1↔Y2 on already used tracks with no new facts.

Rule of thumb: re-visit a station only when the hop_key = (stationId, in, out) is new or Task.context improved (via Inspector). Same hop_key again = spin → prune. Still over-visit? Hard caps → BUDGET.

Restricted switch forces detour (example)

Tracks, Links, hop syntax

Coupler expands the station graph: Links (OUT→IN) plus legal internal pairs on a station. Transparent types fill path only. 

hop syntax:  in : station : out
example:     5 : Y1 : 6     // enter switch Y1 on track 5, leave on 6

Direct transparent types only allow matching numbers. Aggregators / expanders introduce shared Ag tracks with their own capacity rules (mutex vs combine — product policy; DEFAULT exclusive).

First-fit on stable order Coupler multi-sink / agenda sort DECIDED first-fit: ExpandKey lexicographic (§3.7b). Sticky id preferred when equal. No full optimality.
Fill-first / ExpandKey[0] Coupler Lexicographic ExpandKey: preferInUse → preferNonTransparent → distToG → distToTerminal → NeighborRank → names. Not a summed edgeCost.
Sticky snapshot Resolve entry Same Booking + valid relevant world → same route/bindings; skip search.
Prefilter Assembler setup + request + liveData shrink pool before goals (no path context).
Multi-sink couple Coupler ~One fabric search per segment toward all multi-sink goals (Option A).
Oracle++ + ExpandKey distances Before / during Coupler Oracle++ filters goals (reachability + terminal/chain). Same hop BFS feeds ExpandKey distToSegmentGoals / distToTerminal — not a separate f=g+h ranking.

Performance

Dominant cost is almost always: 

time ≈ Σ_segments cost(one multi-sink couple_search)
// ~1 couple per segment attempt (Option A) — not candidates_tried × couple
// backtrack / reopen past last Checkpoint multiplies segments

Drive expansions and goal-pool size down; keep one multi-sink search per segment.

Hot path

  1. Sticky hit → return cached plan (fastest).
  2. Per leg: index by StationType → Prefilter → rank → Oracle++ goal filter → goals.
  3. ~One multi-sink ExpandKey frontier search per segment (not one search per Station / target).
  4. Hard caps: H, V, max_expansions, wall clock.

Data structures (Coupler hot loop)

  • Integer track/station ids; CSR adjacency for Links + legalPairs.
  • Sparse internal maps (only legal in→out pairs).
  • Visited on hop_key / track-state (and visit count if V>1).
  • No string labels inside expand.

Performance is an SLA + caps contract, not “run until optimal.” Measure sticky hit rate, goals entering Coupler, expansions/segment, Oracle++ reject rate.

Graph explosion — more levers

Transparent switches are N:M and switch–switch meshes can explode. Beyond the heuristics above:

Discussed

  • Track-level state + hop_key anti-loop
  • H / V / max expansions
  • Oracle++ goal filter + ExpandKey distances (distToG / distToTerminal)
  • Multi-sink Option A; checkpoint; Prefilter prune
  • Negative sticky so failed Bookings do not rescan when nothing hopeful changed

Additional ideas (not fully designed yet)

Failure reasons

Do not dump the Coupler frontier. Fail at the first pipeline stage that empties options, and attach a small report.

Pipeline (explain at first zero)

Catalog → Prefilter(setup, request, liveData) → Oracle++ goals → Coupler multi-sink path → inspect(tasking) → Budget

Prefilter is path-independent; inspect carries Task context and provisional tasking. Prefer one structured reject reason from Prefilter/Inspector when possible, not a silent empty list.

Stable reason codes

CodeWhenUser-facing gist
NO_CANDIDATESNo Station passes Prefilter for this leg’s requestNothing fits this leg given earlier locks
INSPECT_FAILInspector rejected candidate Task(s) after path (goals tried inside couple)e.g. missing context stamp / track pair illegal
CAPACITY (aka CAPACITY_BLOCKED)Matches exist but tasking/liveData or hop tracks busyStations occupied or Links held by other Bookings
UNREACHABLEOracle++: no geometry within H to any goal / terminalNo Link path to any matching Station
BUDGETHit expansion/hop limitsNo path within search limits
CONTEXT_DEAD_ENDCheckpoints make later legs impossibleEarlier Station choices leave no continuation
POLICYRule forbids combinationDisallowed by policy

Failure report shape

{
  status: "UNSAT",
  code: "CAPACITY",
  legIndex: 2,                    // 0-based demand leg; null if whole-booking
  message: "N→D Links held by B-88",
  stationId: "N-04",
  pathTaken: [ /* hops */ ],
  // optional debug / product extras:
  checkpoints: [
    { leg: 0, stationType: "Refrigerated", station: "R-17" }
    // Normal not yet checkpointed — Docking failed before next-OK lock
  ],
  counts: {
    candidates_before_prefilter: 40,
    after_prefilter: 12,
    oracle_ok: 3
  },
  blockers: [ { booking: "B-88", hop: "5:Y1:6" } ],
  suggestions: [ "Release B-88", "Wait for capacity" ]
}

Checkpoints let you scope the failure: it failed under these locks. That is not a proof another Station would work until you reopen and succeed.

Sticky success & negative cache

SAT (sticky)

Persist plan (route, bindings, planSegments) under demand hash + relevant epochs. On resolve, if still valid → return without re-search.

UNSAT (negative cache)

Cache failure + reason under hopeful relevant world inputs (demand types / samples — not whole plant). Do not thrash thousands of Stations when nothing that could open a solution changed.

EventRetry failed Booking?
Other Booking claims more capacityNo — world tighter
Tasking freed on relevant typesYes
Setup change on relevant station/typeYes
New Link / Link opened / legalPairs changeYes
New Station online (relevant type)Yes
Looser policy (higher H)Yes
This Booking’s legs editedYes
liveData onlyNo auto re-queue

Transparent path stations count when on a SAT route or needed for hope: Link topology, setup, and tasking on relevant stations all affect sticky validity.
